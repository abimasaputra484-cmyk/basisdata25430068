## Petunjuk
Jalankan DDL Kopma Modul 5 pada database kosong, kemudian `p06_data_kopma_25430068.sql`. Jalankan skenario negatif satu per satu. Hasil aktual dan status harus diisi berdasarkan hasil MySQL yang benar-benar muncul.

| ID | Jenis | Input/pengujian | Hasil yang diharapkan | Hasil aktual | Status |
|---|---|---|---|---|---|
| UJ-01 | Positif | Penjualan dengan anggota aktif `id_anggota=1` dan petugas valid | INSERT penjualan diterima | Belum dijalankan | Belum diuji |
| UJ-02 | Positif | Penjualan tanpa anggota (`id_anggota=NULL`) | INSERT diterima, kolom anggota bernilai NULL | Belum dijalankan | Belum diuji |
| UJ-03 | Negatif | UPDATE stok barang menjadi -5 | Ditolak oleh `ck_barang_stok` | Belum dijalankan | Belum diuji |
| UJ-04 | Negatif | INSERT nomor nota yang sudah ada | Ditolak oleh unique `uq_penjualan_nota` (umumnya ERROR 1062) | Belum dijalankan | Belum diuji |
| UJ-05 | Negatif | INSERT detail penjualan dengan qty 0 | Ditolak oleh `ck_detail_qty` | Belum dijalankan | Belum diuji |
| UJ-06 | Negatif | INSERT anggota dengan NIM yang sudah ada | Ditolak oleh `uq_anggota_nim` (umumnya ERROR 1062) | Belum dijalankan | Belum diuji |
| UJ-07 | Negatif | INSERT penjualan dengan `id_petugas` yang tidak ada | Ditolak oleh `fk_penjualan_petugas` (umumnya ERROR 1452) | Belum dijalankan | Belum diuji |
| UJ-08 | Negatif | UPDATE tanpa WHERE ketika `sql_safe_updates=1` | Ditolak oleh safe update (umumnya ERROR 1175) | Belum dijalankan | Belum diuji |
| UJ-09 | Positif | UPDATE stok barang dengan WHERE berdasarkan PK | UPDATE baris yang dituju berhasil | Belum dijalankan | Belum diuji |
| UJ-10 | Positif | Hapus penjualan uji yang memiliki detail | Penjualan terhapus dan detail ikut terhapus karena ON DELETE CASCADE | Belum dijalankan | Belum diuji |
| UJ-11 | Negatif | Hapus petugas yang masih direferensikan penjualan | Ditolak oleh FK `fk_penjualan_petugas` | Belum dijalankan | Belum diuji |
| UJ-12 | Batasan aturan bisnis | Masukkan qty penjualan lebih besar daripada stok barang | Dapat diterima jika qty positif karena belum ada constraint lintas tabel yang memeriksa stok | Belum dijalankan | Belum diuji |

## SQL pengujian (jalankan per bagian)

```sql
USE kopma_068;

-- UJ-03: stok negatif
UPDATE barang SET stok_barang=-5 WHERE id_barang=1;

-- UJ-04: nomor nota duplikat
INSERT INTO penjualan
(no_nota_penjualan,tgl_penjualan,id_petugas,id_anggota,bayar_penjualan)
VALUES ('PJ-2609-0142','2026-09-12 10:00:00',1,1,10000);

-- UJ-05: qty nol; gunakan penjualan dan barang yang sudah ada
INSERT INTO detail_penjualan
(id_penjualan,id_barang,qty_detail_penjualan,harga_satuan_detail_penjualan)
VALUES (1,6,0,6000);

-- UJ-06: NIM duplikat
INSERT INTO anggota
(no_anggota,nim_anggota,nama_anggota,prodi_anggota,no_hp_anggota)
VALUES ('AG0099','2543006801','Anggota Duplikat','Sosiologi','080000000099');

-- UJ-07: petugas tidak dikenal
INSERT INTO penjualan
(no_nota_penjualan,tgl_penjualan,id_petugas,id_anggota,bayar_penjualan)
VALUES ('PJ-TEST-007','2026-09-12 10:00:00',999,1,10000);

-- UJ-08: safe update tanpa WHERE
SET SESSION sql_safe_updates=1;
UPDATE barang SET harga_jual_barang=harga_jual_barang+100;
-- Pulihkan pengaturan sesi jika diperlukan:
SET SESSION sql_safe_updates=0;

-- UJ-09: UPDATE aman dengan WHERE PK
UPDATE barang SET stok_barang=stok_barang+1 WHERE id_barang=1;

-- UJ-10: uji cascade memakai transaksi agar data awal pulih
START TRANSACTION;
INSERT INTO penjualan
(no_nota_penjualan,tgl_penjualan,id_petugas,id_anggota,bayar_penjualan)
VALUES ('PJ-TEST-010','2026-09-12 11:00:00',1,NULL,1000);
SET @id_uji = LAST_INSERT_ID();
INSERT INTO detail_penjualan
(id_penjualan,id_barang,qty_detail_penjualan,harga_satuan_detail_penjualan)
VALUES (@id_uji,6,1,6000);
DELETE FROM penjualan WHERE id_penjualan=@id_uji;
SELECT COUNT(*) AS sisa_detail FROM detail_penjualan WHERE id_penjualan=@id_uji;
ROLLBACK;

-- UJ-11: petugas yang masih dipakai penjualan
DELETE FROM petugas WHERE id_petugas=1;

-- UJ-12: uji aturan stok yang belum dijaga constraint.
-- Jalankan transaksi ini sendiri; hasil INSERT diperkirakan diterima,
-- kemudian ROLLBACK agar tidak mengubah data.
START TRANSACTION;
INSERT INTO penjualan
(no_nota_penjualan,tgl_penjualan,id_petugas,id_anggota,bayar_penjualan)
VALUES ('PJ-TEST-012','2026-09-12 12:00:00',1,NULL,1000000);
SET @id_stok_uji = LAST_INSERT_ID();
INSERT INTO detail_penjualan
(id_penjualan,id_barang,qty_detail_penjualan,harga_satuan_detail_penjualan)
VALUES (@id_stok_uji,1,10000,5000);
ROLLBACK;
```

## Catatan analisis
UJ-12 menguji keterbatasan aturan bisnis. Tabel `barang` memiliki CHECK agar `stok_barang` tidak negatif, sedangkan tabel `detail_penjualan` memiliki CHECK agar kuantitas lebih dari nol. Akan tetapi, tidak ada constraint yang membandingkan kuantitas penjualan dengan stok barang. Akibatnya, database dapat menerima kuantitas penjualan yang melebihi stok selama nilai lainnya valid. Hal ini menjadi *design debt* yang perlu ditangani pada pengembangan berikutnya.
